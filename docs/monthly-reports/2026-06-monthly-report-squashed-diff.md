## 主要成果

### 1. 实盘任务重启恢复: 让正在跑的任务不怕服务重启

**解决的问题**

实盘交易任务一旦启动，就可能已经在交易所留下持仓、止损单或其他未完成订单。如果服务重启后系统只看本地内存，就会失去“哪些任务还在运行”的上下文。更糟的是，错误的恢复逻辑可能重复启动任务、漏掉状态，甚至取消仍然有效的交易所订单。

**最终完成的能力**

- 服务启动时会从数据库读取 `RUNNING` 状态任务，并把保存的任务配置恢复成可运行的 `TaskConfig`。
- 服务端启动任务时会跳过已经等待恢复的同类任务，避免“配置文件启动一次、数据库恢复再启动一次”的重复执行。
- 恢复任务走独立的 `recover_task` 路径：恢复时重新绑定交易订单上下文，但不会取消已经存在的交易所订单。
- 恢复过程在后台并发执行，并有并发上限，避免大量任务恢复时阻塞整个服务。
- 任务启动失败时会持久化为 `FAILED` 状态，并记录 `error_message`，让前端和 API 能看到失败原因。

**为什么重要**

这让实盘交易系统更接近一个长期运行服务，而不是一个一次性脚本。普通用户不需要理解进程、内存和数据库的区别，只需要知道：服务重启以后，系统能更可靠地找回正在运行的任务，并减少重复启动或误取消订单的风险。

**关键位置**

- `src/trader/app/app.py`
- `src/trader/task/task_manager.py`
- `src/trader/database/migrations/0007_task_error_message.py`

### 2. 实盘资金预留: 启动前先确认钱是否真的够用

**解决的问题**

在自动交易里，“账户余额看起来够”不等于“这个任务可以安全启动”。同一个账户可能同时有多个任务，保证金账户还涉及可借额度、冻结资金和借贷限制。如果系统不提前预留资金，多个任务可能同时认为自己有钱，最终在下单时失败，或者造成超出预期的资金占用。

**最终完成的能力**

- 新增 `account_fund_reservations` 数据表，记录每个实盘任务对账户、资产和金额的资金预留。
- 任务启动前会计算所需资金；对于保证金任务，会把可用余额和最大可借额度一起纳入可操作能力判断。
- 如果已有任务占用了同一账户同一资产的资金，新任务会把这部分 active reservation 算进去，避免重复占用。
- 任务完成、失败、关闭或恢复结束时，会释放对应预留，避免预留记录长期占用资金能力。
- 当资金不足时，日志会写出清楚的拒绝原因，包括需要金额、余额、可借额度、借贷限制和已预留金额。

**为什么重要**

这相当于给自动交易加了一道“先验预算”。普通用户可以把它理解为：系统在真正下单前先帮你检查这笔交易会不会和其他任务抢同一笔钱，尤其是在 margin 场景下，不再只看现货余额。

**关键位置**

- `src/trader/database/account_fund_reservation.py`
- `src/trader/database/migrations/0006_account_fund_reservations.py`
- `src/trader/task/task_manager.py`
- `tests/test_account_fund_reservation.py`

### 3. 用户级交易凭证和账户能力展示: 多用户实盘不再只依赖全局账号

**解决的问题**

实盘交易如果只使用全局交易所 API Key，在多用户环境下会有两个问题：一是很难隔离不同用户的账户，二是用户看到的账户余额、可借额度和实际执行任务的凭证可能不是同一个上下文。

**最终完成的能力**

- 新增用户交易所凭证上下文，通过用户保存的 Binance API Key / Secret 构建交易所连接。
- 读取用户凭证时要求 `TRADER_SECRET_KEY` 可用，避免加密凭证无法解密时静默失败。
- 账户页新增“策略可操作资金”视图，展示借贷资产、当前最大可借和当前可操作金额。
- 账户列表中增加可借、可操作字段，并显示资金被 open orders 锁定的来源。
- 账户页读取交易所失败时保持页面可用，并把错误展示给用户，而不是让页面整体不可用。

**为什么重要**

普通用户关心的是“系统到底准备用哪个账户交易”和“现在还能操作多少钱”。这部分工作把实盘交易的账户上下文显式化，也让资金不足、凭证缺失、交易所读取失败这些问题更容易被定位。

### 4. 订单追踪与清理: 让交易所订单能关联回任务

**解决的问题**

交易机器人下单后，交易所看到的是一批订单。如果订单没有任务标识，排查时很难回答“这个订单是谁下的、属于哪个任务、是否应该清理”。同时，任务启动或停止时如果遗留旧的 open orders，可能影响下一次交易。

**最终完成的能力**

- CCXT driver 支持绑定订单上下文，为后续订单生成结构化 `clientOrderId`。
- `clientOrderId` 包含任务 ID、策略简称和递增序号，便于从交易所订单追溯到 ChainerTrader 任务。
- 任务启动和关闭时可以按配置 symbol / 运行任务 symbol 清理 open orders，减少旧订单干扰新任务。
- 恢复任务时不会清理 open orders，因为恢复场景下这些订单可能正是任务原本有效的保护单或未完成订单。
- 关闭任务时会同时持久化任务状态、释放资金预留，并尝试清理相关 open orders。

**为什么重要**

这部分工作让订单生命周期更可控。普通用户可以理解为：系统给自己下的订单贴了标签，并且在任务开始/结束时更主动地处理旧订单；但在服务重启恢复时，系统不会粗暴删除可能仍然有效的订单。

**关键位置**

- `src/trader/exchange/ccxt_driver.py`
- `src/trader/task/task_manager.py`
- `tests/test_ccxt_exchange_driver.py`
- `tests/test_task_manager_order_lifecycle.py`

### 5. 任务控制台可观测性: 失败、历史和操作记录更容易看懂

**解决的问题**

实盘任务失败时，如果用户只能看到“没有跑起来”而看不到具体原因，就只能去翻服务端日志。任务历史很多时，如果没有分页和筛选，任务页会变慢，也很难找到目标任务。

**最终完成的能力**

- 任务页支持按任务类型、币种、周期、策略和任务状态筛选。
- 任务列表支持分页，避免历史任务过多时页面过重。
- 任务启动失败会显示 `FAILED` 状态和错误信息。
- 任务详情里增加操作记录入口，操作记录通过 API 分页读取。
- 任务配置表单提交后保留输入状态，失败后用户不需要从头重新填写。
- 任务 stop / rerun 的用户权限检查和 API 行为更一致。

**为什么重要**

这让任务控制台从“开发者调试页面”更接近“操盘和运维页面”。普通用户能直接在页面上看到任务为什么失败、历史操作有哪些、下一步该重跑还是停止，而不是依赖开发人员查日志。

**关键位置**

### 6. 回测与优化数据准备: 减少“数据不完整但报告看起来正常”的风险

**解决的问题**

回测和优化最怕数据覆盖不完整：如果某段 K 线缺失，结果可能看起来正常，但实际已经偏离真实市场。之前数据准备更像“取到了就用”，对缺口、缓存范围和补下载的表达不够明确。

**最终完成的能力**

- Dataset resolver 会检测请求区间内缺失的 K 线范围。
- 如果允许自动下载，会按缺失区间补数据；如果下载预算不足或下载失败，会明确返回失败原因。
- availability 表增加 cached open time range，避免重复导出和重复下载同一段已确认覆盖的数据。
- 本地 CSV cache 会按天级区间复用，并校验缓存行数与数据库行数是否一致。
- 修复 workbench report asset paths，优化报告里的资源路径更稳定。

**为什么重要**

对普通用户来说，回测报告只有在底层数据完整时才有参考价值。这部分工作让系统更明确地知道“数据够不够”“哪里缺”“能不能补”，从而减少错误数据带来的错误判断。

**关键位置**

- `src/trader/task/dataset_resolver.py`
- `src/trader/database/availability.py`
- `src/trader/database/migrations/0005_availability_cached_range.py`
- `src/trader/task/optimization_workbench.py`
- `tests/test_dataset_resolver.py`

6 月整体 diff 中，测试目录占文件变化的约 29%。新增和扩展的测试覆盖了资金预留、订单生命周期、凭证路由、任务恢复、RPC 页面、dataset resolver、execution state 和 live auto execution 等关键路径。

这说明 6 月不是单纯增加页面或配置，而是在实盘交易关键路径上增加了更多自动化防护。尤其是资金预留、任务恢复和订单清理，都是一旦出错就可能影响真实账户的高风险行为，因此测试投入是必要的。

## 对用户的实际影响

- 实盘任务重启后更容易恢复，减少因为服务重启导致任务状态丢失的风险。
- 自动交易启动前会更认真地检查资金和保证金能力，减少启动后才失败的情况。
- 用户能在账户页看到可借和可操作资金，资金判断更接近真实交易能力。
- 交易所订单带有任务上下文，出现问题时更容易定位订单来源。
- 任务页能直接展示失败原因、分页历史和操作记录，排障不再完全依赖后台日志。
- 回测和优化的数据准备更谨慎，降低数据缺口导致错误报告的概率。

## 后续关注

- 6 月的变化集中在实盘交易生命周期，后续应继续用组合场景验证: 服务重启、任务恢复、资金不足、margin borrow blocked、open orders 残留、任务关闭同时发生时，系统行为是否仍然一致。
- 资金预留和订单清理都涉及真实账户，应在小规模 live smoke 中持续验证日志、页面展示和交易所实际订单是否一致。
- `clientOrderId`、资金预留规则、用户凭证要求和任务恢复边界应补充到用户手册或运维手册，方便非开发人员排障。
