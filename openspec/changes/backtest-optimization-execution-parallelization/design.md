## Context

当前参数优化执行链路已经支持参数组合展开和 `dataset_ref` 复用，但调度方式仍然偏粗放：
- 唯一数据集准备阶段按 dataset key 串行执行，导致多币种、多周期任务在开始前存在明显的顺序瓶颈
- 样本回测阶段按“每个样本一个 `multiprocessing.Process`”直接 fan-out，样本数增长时会出现进程过量、调度开销高、资源利用不稳定的问题
- 父进程当前承担了过多样本实例化责任，不利于受控并行和轻量调度

本次 change 聚焦“优化执行调度/并行化”，在不改变参数优化结果语义和报告契约的前提下，把执行链路升级为受控并行调度。

## Goals / Non-Goals

**Goals:**
- 将参数优化运行拆分为“唯一数据集准备”和“样本回测执行”两个受控并行阶段
- 让唯一数据集准备具备有限并行能力，并继续复用现有 `dataset_ref` 机制
- 将样本回测执行改为基于 `os.cpu_count()` 的进程池，避免按样本数无限制创建进程
- 将 worker 边界收紧为轻量任务规格，由子进程内部创建 `CSVData`、`Node` 和策略实例
- 保持现有 `optimization_run_id`、单次报告、聚合报告和失败记录契约兼容

**Non-Goals:**
- 不修改参数搜索语义、参数评分逻辑或聚合算法
- 不将本地多进程执行扩展为分布式调度系统
- 不重写 `DatasetResolver` 的数据覆盖检查、补数或缓存格式
- 不在本次 change 中引入新的交易所数据源或新的执行后端

## Decisions

### 决策 1：参数优化运行采用两阶段调度模型

**选择**：每次参数优化运行先构建唯一数据集任务并完成数据准备，再构建样本执行任务并提交到进程池。

**备选方案**：
- 保持现有单阶段流程，在展开样本时按需准备数据
- 将数据准备和样本执行完全流水线化

**理由**：两阶段模型更适合复用现有 `dataset_ref` 机制，也更容易在 manifest、失败记录和日志维度保持清晰边界。与更激进的流水线相比，它牺牲了一部分重叠执行机会，但显著降低了调度复杂度和失败传播难度。

### 决策 2：唯一数据集准备采用独立的有限并行上限

**选择**：唯一数据集准备不再串行，而是通过单独的受控并发上限执行，并与样本执行的 worker 数解耦。

**备选方案**：
- 继续串行准备数据集
- 将数据准备并发数直接绑定到 `os.cpu_count()`
- 对所有数据集无上限并发准备

**理由**：数据准备主要受数据库 I/O、CSV 物化和交易所 API 补数影响，并不属于典型 CPU-bound 工作。将它与样本执行进程池解耦，能避免在 CPU 足够多时把数据库或交易所 I/O 压爆，也避免把“有限并行”误做成“无限制 fan-out”。

当前 `DatasetResolver` 虽然以 `async` 形式暴露，但内部依赖的数据库查询和交易所 K 线拉取仍然是阻塞 I/O。实现有限并行时，不能把“简单套一层 `asyncio.gather()`”当作真实并发；需要使用线程化 offload 或等价机制，将阻塞 I/O 放到受控的并发执行单元中。

### 决策 3：样本执行使用基于 CPU 核数的进程池

**选择**：样本回测通过进程池执行，有效 `max_workers` 来源于 `os.cpu_count()`；当样本数超过 worker 数时，其余样本排队等待，而不是继续拉起额外进程。

**备选方案**：
- 继续按样本数直接创建并启动多个 `Process`
- 使用线程池执行回测
- 将 worker 数设置为固定常量

**理由**：回测执行主要消耗 CPU，进程池更适合隔离 Backtrader 运行时和 Python GIL 影响。以 CPU 核数作为默认并发上限，是本地多核机器上最稳定的基线策略，也符合“受控并行”而非“资源争抢”的目标。

### 决策 4：父进程只分发轻量样本任务规格

**选择**：父进程不再预先构造 `CSVData`、`Node` 或其他重型运行时对象，而是仅向 worker 分发轻量任务规格，例如：
- `dataset_ref.path`
- `symbol` / `interval`
- `strategy`
- `params`
- `optimization_run_id`
- `param_id`
- 报告输出上下文

子进程在收到任务后自行完成 CSV 数据源、策略实例和执行链路对象的构造。

**备选方案**：
- 继续在父进程构造回测对象，再传入子进程
- 将完整 K 线列表通过进程间通信直接发送给 worker

**理由**：轻量任务规格更适合进程池调度，能降低对象序列化、跨进程复制和父进程预处理成本，也能让 worker 生命周期与单次回测样本严格对齐。

### 决策 5：并行化不得改变报告与失败传播契约

**选择**：并行执行仅改变调度方式，不改变结果语义。`optimization_run_id`、单次 JSON 报告、manifest、aggregate 和 failures 的结构保持兼容；当数据集准备失败或 worker 执行失败时，失败原因必须继续被结构化记录。

**备选方案**：
- 为并行执行单独设计新的报告目录结构
- 对并发场景只保留汇总统计，不保留单样本失败明细

**理由**：报告契约已经被前一个 change 和自动化测试固定下来。并行化是底层执行优化，不应迫使上层消费方修改分析逻辑。

### 决策 6：样本执行结果应通过可序列化返回值回传

**选择**：样本 worker 应返回可序列化的结果载荷，由调度器统一汇总日志、统计消息和样本报告，而不是继续依赖共享可变列表作为主通道。

**备选方案**：
- 继续使用 `Manager().list()` 让 worker 追加结果
- 让 worker 直接写入聚合文件

**理由**：进程池模型更适合“任务提交 -> 结果返回”的收集方式。可序列化结果回传有助于明确 worker 边界，并减少共享状态带来的调试复杂度。单次报告仍可由 worker 写文件，但运行级 manifest/aggregate/failures 应继续由调度器统一收口。

### 决策 7：普通回测兼容优先，优化调度先覆盖参数优化路径

**选择**：本次 change 优先覆盖参数优化批量回测路径，确保普通单次回测配置仍可按现有语义运行。

**备选方案**：
- 同步重写所有 `BACK_TRADER` 执行路径
- 仅对参数优化新增独立 CLI，而不复用现有任务入口

**理由**：参数优化路径是当前并行化瓶颈最明显的场景。先在该路径上建立调度边界，可以以较小风险验证机制，再决定是否向普通批量回测统一收敛。

## Risks / Trade-offs

- **数据准备并发过高会放大数据库/API 压力**：因此需要单独的准备阶段并发上限，而不是直接复用样本 worker 数
- **把阻塞 I/O 误当成协程并发，会得到名义 async、实际串行的实现**：需要在线程化/等价 offload 方案下验证真实并发行为
- **父进程不再构造运行时对象后，错误会更集中地出现在子进程**：需要明确结果回传和失败序列化契约
- **两阶段调度减少了数据准备与计算重叠**：会损失一部分理论吞吐，但换来更清晰的故障边界和更低的实现复杂度
- **进程池要求任务规格可稳定序列化**：任务输入模型必须保持轻量和显式，避免夹带不可 picklable 的对象

## Migration Plan

1. 为“执行调度/并行化”建立独立 OpenSpec 能力定义
2. 在任务层引入两阶段调度结构，先组织唯一数据集作业，再组织样本作业
3. 为数据准备层补充有限并行调度，同时保持现有 `dataset_ref` 与失败契约
4. 用基于 `os.cpu_count()` 的进程池替换无限制进程 fan-out，并将运行时对象构造迁移到 worker 内部
5. 补齐并发上限、结果兼容性和失败传播测试

## Open Questions

- 唯一数据集准备的默认并发上限是否需要额外暴露为配置项，还是先保持内部固定策略
- 普通非优化批量回测未来是否也应复用同一调度器，还是继续保留独立执行路径
