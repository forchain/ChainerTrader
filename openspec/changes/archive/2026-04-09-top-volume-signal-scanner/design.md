## Context

仓库当前已有以下可复用基础能力：

- `src/trader/task/update_klines_task.py` 已实现 MongoDB 优先的增量更新逻辑，可在给定时间范围内补齐缺失 K 线
- `src/trader/database/kline.py` 已支持按时间范围读取某个 `symbol + interval` 的历史 K 线
- `src/trader/exchange/binance/exchange.py` 已提供 Binance REST 访问能力
- `scripts/run_macd_triple_divergence_report.py` 已证明可以独立运行默认策略并产出结构化结果

本次 change 的目标不是再做一个完整回测工作流，而是新增一个“扫描器”入口：面向多个标的和多个周期，在限定的最近窗口上收集入场信号。

## Goals / Non-Goals

**Goals:**
- 自动选出 Binance 现货 `USDT` 交易对按成交额排名前 10 的标的
- 排除稳定币交易对，减少榜单失真
- 在执行策略前，先确保 MongoDB 中 `1d` 最近 1 个月和 `1h` 最近 1 周数据完整
- 扫描阶段只从数据库读取，不直接拿 API 数据喂策略
- 默认支持 `macd_triple_divergence`，同时保留策略可配置能力
- 只记录窗口内命中的 `LONG` / `SHORT` 入场信号
- 对全部命中信号按时间全局排序输出

**Non-Goals:**
- 不实现出场信号、止损、止盈的统一导出
- 不在本次 change 中做策略参数优化
- 不修改 MongoDB 的底层表结构
- 不扩展到非 Binance 交易所

## Decisions

### 决策 1：Top 10 以 Binance 现货 `USDT` 交易对成交额为准，而非 CoinMarketCap 市值

**选择**：直接使用 Binance 现货市场数据源，筛选 `quoteAsset == USDT` 的现货交易对，并按成交额排序取前 10。

**备选方案**：
- 使用 CoinMarketCap 市值前 10 再映射到 Binance
- 使用手工 symbol 列表

**理由**：
- 用户已明确要求按 Binance 现货成交额取前 10
- 这比“市值前 10”更贴近实际可交易流动性
- 避免外部榜单和 Binance 可交易列表不一致

### 决策 2：稳定币交易对需要显式排除

**选择**：维护一组稳定币基础资产黑名单，例如 `USDT`、`USDC`、`BUSD`、`FDUSD`、`TUSD`、`USDP`、`DAI` 等；任何 base asset 命中黑名单的 `XXXUSDT` 交易对不参与排名。

**理由**：
- 稳定币交易对成交额通常很高，但对趋势策略扫描价值低
- 用户已明确要求排除稳定币
- 用黑名单实现最直接，且后续可扩展

### 决策 3：扫描前必须先补库，且策略执行只读数据库

**选择**：脚本分成两个阶段：
1. 更新数据库，补齐所需窗口
2. 从数据库读取窗口数据执行策略

**理由**：
- 用户明确要求“首先应该去更新数据库，确保数据库里面的数据是完整的”
- 统一从 DB 读取可保证不同策略执行的数据来源一致
- 复用已有 DB-first 逻辑，减少重复下载

### 决策 4：窗口范围固定为 `1d = 最近 1 个月`、`1h = 最近 1 周`

**选择**：默认窗口直接在脚本中提供，并通过 CLI 参数允许后续调整。

**理由**：
- 这是用户当前明确指定的默认需求
- 固定默认值可以先完成最小可用扫描器
- 后续保留参数化空间，不影响当前实现

### 决策 5：扫描结果只记录 `LONG` / `SHORT` 入场信号

**选择**：统一定义“命中的信号”为策略产生的入场事件，不包含平仓、止损、止盈。

**理由**：
- 用户已明确要求“只要策略产生 LONG/SHORT 入场信号就记一条”
- 当前参考脚本 [scripts/run_macd_triple_divergence_report.py](/Users/tonyoutlier/.codex/worktrees/f3be/ChainerTrader/scripts/run_macd_triple_divergence_report.py) 也主要围绕入场信号使用
- 当前仓库尚未形成统一的出场信号导出接口，本次不扩大范围

### 决策 6：全局输出按信号时间排序，保留窗口内全部命中

**选择**：不做“每个标的只保留最新一条”的收缩，而是保留窗口内所有命中的 `LONG` / `SHORT` 信号，最后全局按时间排序。

**理由**：
- 用户已明确要求“输出窗口内所有命中的信号，再全局按时间排序”
- 这样更适合回顾最近一段时间的市场扫描结果

### 决策 7：输出同时支持终端展示与 JSON 结构化结果

**选择**：脚本默认打印简洁表格，并可选输出 JSON 文件。

**理由**：
- 终端输出便于人工快速查看
- JSON 输出便于后续自动化、报告、或二次分析

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|---------|
| Binance 成交额接口字段定义与预期不一致 | 实施时以 Binance 实际接口返回字段为准，并在测试中覆盖排序逻辑 |
| 稳定币名单不完整导致漏排除 | 将稳定币黑名单集中定义，便于补充和测试 |
| 默认策略没有统一的“信号事件导出”接口 | 为默认策略增加最小信号收集适配层，并把接口设计成可复用 |
| 批量扫描涉及多个 symbol 与两个周期，运行时间可能上升 | 先限定 Top 10 和两个固定窗口，控制单次扫描规模 |
| 某些 Top 10 交易对刚上线或历史不足 | 输出中明确该 symbol/interval 的数据不足或跳过原因 |

## Migration Plan

1. 新增批量扫描脚本，定义 CLI 参数和主流程
2. 接入 Binance 现货成交额榜单读取与稳定币排除逻辑
3. 复用现有增量更新逻辑，补齐 Top 10 标的的 `1d` / `1h` 数据
4. 从数据库读取最近窗口 K 线并喂给默认策略
5. 收集 `LONG` / `SHORT` 入场信号并按时间排序输出
6. 增加测试覆盖：选币过滤、补库范围、信号输出格式

**回滚**：本次 change 以新增脚本和辅助逻辑为主；若需回滚，删除新增扫描入口及其适配层即可，不影响现有功能。
