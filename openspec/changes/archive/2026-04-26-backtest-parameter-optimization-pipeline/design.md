## Context

当前历史回测执行链路为：

`task config -> parse_task_config() -> BackTraderTask.start() -> Node.start() -> cerebro.run()`

系统已经具备一些与本次变更相关的基础能力：
- `TaskConfig` 已支持按币种和策略展开多个回测任务
- `BackTraderTask` 已支持优先读取 CSV，其次读取 MongoDB，数据库缺失时可在 `auto_download=true` 下自动补数
- `UpdateKlinesTask` 已具备按时间区间补数到数据库的逻辑
- `BacktestReportAnalyzer` 已支持输出单次结构化 JSON 报告

但当前系统仍存在三个结构性缺口：
1. 参数尚未成为回测维度，策略参数通常只以类默认值存在
2. 数据获取逻辑分散在具体任务内部，尚未形成统一的数据准备机制
3. 单次报告缺少参数与运行上下文，也缺少跨币种、跨周期的聚合优化报表

## Goals / Non-Goals

**Goals:**
- 支持参数空间搜索，并保持现有单次回测能力向后兼容
- 建立统一的数据准备机制，避免未来重复实现“查库、补数、缓存”逻辑
- 使用内部透明缓存提升同批参数回测的执行效率和结果一致性
- 生成适合 Agent 自动分析的单次与聚合报表
- 提供自动化测试，支持长期迭代和回归检查

**Non-Goals:**
- 不实现 Bayesian optimization
- 不实现遗传算法或强化学习优化器
- 不要求用户显式维护回测 CSV 文件
- 不改动现有策略交易逻辑
- 不将综合评分包装成不可解释的黑盒

## Decisions

### 决策 1：引入统一的 Historical Dataset Resolver

**选择**：将历史回测数据准备抽象为统一机制，由独立的数据准备层负责数据库覆盖检查、缺口补齐、缓存物化和 `dataset_ref` 返回。

**备选方案**：
- 继续在 `BackTraderTask` 内部堆叠查库、补数、缓存逻辑
- 在参数优化流程里私有实现一套数据准备逻辑

**理由**：数据准备不是参数优化的私有需求，而是所有历史回测共享的底层能力。统一的数据准备层可以避免未来在训练集回测、验证集回测、批量筛选和参数优化中重复实现同类逻辑。

### 决策 2：数据准备按数据集键去重

**选择**：以 `(symbol, interval, start_time, end_time)` 作为数据集键，对同一批回测中的数据准备请求去重。

**备选方案**：
- 按单个回测任务准备数据
- 将参数组合纳入数据集键

**理由**：参数只影响策略逻辑，不影响底层 K 线数据。同一数据集键下的多个参数组合应共享同一份底层数据，以减少重复查库和重复补数，并确保同批结果可比较。

### 决策 3：本地数据文件采用内部透明缓存

**选择**：在数据库数据准备完成后，系统将目标区间物化为内部透明缓存文件，回测层只消费 `dataset_ref`，不要求用户显式维护 CSV 输入文件。

**备选方案**：
- 继续要求用户手工准备 CSV
- 使用内存对象直接在多进程间传递 K 线列表
- 引入自定义二进制缓存格式

**理由**：内部透明缓存能复用现有 CSV 读取链路，降低实现风险，同时减少多进程间复制大块内存数据的开销。用户仍然只配置逻辑参数，不必了解缓存细节。

### 决策 4：参数搜索配置仅绑定单策略任务

**选择**：带有 `param_grid` 或 `param_combinations` 的任务条目只允许声明一个策略。

**备选方案**：
- 允许一个任务条目绑定多个策略并共享参数空间

**理由**：不同策略的参数命名空间天然冲突，强行共享会让 schema、校验和报表都变脏。保持单策略任务边界更清晰，也更利于参数标识与聚合结果的一致性。

### 决策 5：优化运行使用 `optimization_run_id` 管理产物

**选择**：每次参数优化执行生成唯一的 `optimization_run_id`，并将该 run 的单次报告、聚合报告、榜单视图和失败样本统一放在 `reports/optimizations/<optimization_run_id>/` 下。

**备选方案**：
- 继续沿用散落在 `reports/` 根目录的时间戳文件

**理由**：目录化运行产物更适合 Agent 自动分析、回归测试和人工追溯。`optimization_run_id` 也能稳定地串联 manifest、单次样本、聚合结果和失败记录。

### 决策 6：首版同时提供综合榜和超额收益榜

**选择**：聚合结果至少输出两个正式榜单：
- `by_score`：综合榜
- `by_excess_return`：超额收益榜

**备选方案**：
- 只输出总收益榜
- 只输出单一综合分数

**理由**：总收益在单边行情中容易误导，超额收益更接近策略是否真正创造价值；但只给一个黑盒综合分也不利于判断。双榜结构既保留收益视角，又突出稳健性视角。

### 决策 7：`score_v1` 使用透明、可版本化的启发式规则

**选择**：首版综合评分使用固定区间归一化的启发式规则，并显式记录 `score_version`。

**备选方案**：
- 直接按总收益率排序
- 使用 run 内动态 min-max 归一化
- 先不提供综合分

**理由**：固定区间归一化比 run 内相对归一化更适合跨 run 对比。评分规则本身不追求交易领域标准答案，但必须足够透明，便于未来演进和自动化分析。

## Risks / Trade-offs

- **数据库覆盖检查只看首尾，不看中间缺口** → Dataset Resolver 必须显式校验区间连续性，中间缺口也要触发补数
- **参数组合爆炸导致执行时间不可控** → 首版由用户控制搜索空间，后续可增加组合数预估或上限
- **缓存与数据库状态不一致** → 统一由 Dataset Resolver 生成缓存，并在单次报告中记录 `dataset_ref`
- **综合评分不被信任** → 保留超额收益榜，并在聚合结果中同时暴露关键原始指标与 `score_version`
- **失败样本被静默忽略** → 所有准备失败或执行失败样本都必须进入 `failures/` 并进入 manifest

## Migration Plan

1. 为参数优化引入新的 OpenSpec 能力定义与测试契约
2. 抽象统一的数据准备入口，将现有查库与补数逻辑迁移到 Dataset Resolver
3. 在不破坏现有普通回测的前提下，引入内部透明缓存与 `dataset_ref`
4. 扩展任务配置和回测展开逻辑，支持参数空间搜索
5. 增强单次报告，并新增聚合优化报告与榜单输出
6. 补齐数据准备、参数展开、聚合排名和报表契约测试

**回滚**：普通回测保持兼容。如果需要回滚参数优化能力，可移除参数搜索配置解析、聚合报表输出和 run 目录化产物；数据准备机制可以保留为普通回测共用基础能力。

## Open Questions

- `score_v1` 的固定区间归一化边界是否需要按不同策略类型细分，还是先采用全局通用阈值
- 内部透明缓存首版是否完全复用现有 Binance CSV 格式，还是需要补充更强的元数据索引文件
- 普通单次回测是否也应逐步迁移到统一 Dataset Resolver，还是先只覆盖参数优化路径
