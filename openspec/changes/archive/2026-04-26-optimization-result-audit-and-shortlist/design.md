## Context

当前优化 pipeline 已经能展开参数矩阵、运行批量回测并输出聚合排名，但系统仍把“结果展示”和“结果可信度”混在一起。现状存在三个结构性缺口：

- 优化结果缺少独立审计层，参数失效、退出原因缺失和可疑重复行为只能依赖人工嗅探
- 聚合排名直接面对原始参数组合，无法先做行为去重与局部最优筛选
- 现有单次报告虽然包含交易明细，但缺少足够的中间风控状态，无法支持参数覆盖率分析和交易行为指纹

这次变更要在现有 pipeline 之上新增一条“审计 -> 聚类 -> 局部最优 -> shortlist”的后处理链路。目标不是替代原始报表，而是让系统先判断结果能否信，再给出适合实盘决策的候选池。

## Goals / Non-Goals

**Goals:**
- 为关键参数提供覆盖率审计，区分生效、未触发、被覆盖和可疑失效
- 为每个优化样本生成稳定的交易行为指纹，支持精确行为去重
- 按 `strategy + symbol + interval` 聚类和筛选，输出局部最佳参数
- 生成机器可读的 `audit/clusters/local_best/shortlist` 产物，并提供基础 HTML 视图
- 建立一套可长期独立迭代的自检闭环，让脚本和 Agent 能在人工介入前发现明显异常

**Non-Goals:**
- 不在 V1 实现跨市场全局组合优化或资金分配
- 不在 V1 引入复杂黑盒评分或高级相似度聚类算法
- 不把 Agent 审查作为唯一审计手段；硬规则审计必须优先
- 不改变策略的交易语义，只修正报告和风控链路的可解释性与独立性

## Decisions

### 决策 1：把优化审计做成独立产物层，而不是把规则塞进排名 HTML

**选择**：每次 optimization run 完成后新增 `audit.json`、`fingerprints.json`、`clusters.json`、`local_best.json`、`shortlist.json` 等结构化产物，HTML 只是这些数据的展示层。

**备选方案**：
- 继续只生成 `rankings/index.html`，在前端页面中动态判断异常
- 在现有 `aggregate.json` 中零散追加字段，不形成独立审计产物

**理由**：审计结果需要被脚本、Agent 和后续 workflow 复用，必须先是机器可读数据，再由 HTML 消费。把审计逻辑塞进页面会让自动化检查不可复用，也难以持续迭代。

### 决策 2：参数覆盖率采用四层证据模型

**选择**：对每个关键参数分别统计：
- `value_coverage`
- `path_coverage`
- `opportunity_coverage`
- `effect_coverage`

并输出统一状态：`effective`、`no_opportunity`、`inactive`、`shadowed_or_overridden`、`suspicious`。

**备选方案**：
- 只统计参数取值和最终收益差异
- 只统计代码路径是否进入，不检查效果

**理由**：仅看收益会误伤“中间状态变化但收益未变”的正常参数；仅看路径又无法发现参数虽然执行了却被覆盖。四层证据更接近“代码覆盖率 + 行为覆盖率”的组合。

### 决策 3：交易行为聚类先做 Exact，再保留 Similar 作为后续扩展

**选择**：V1 先基于精确执行指纹做完全重复行为聚类，只要逐笔交易的方向、时间、价格、退出原因和关键风控状态完全一致，就视为同一行为簇。

**备选方案**：
- 一开始就做相似度聚类
- 只看收益、交易数和回撤来判断重复

**理由**：Exact clustering 最稳，最适合抓参数不同但行为完全一致的实现 bug。相似度聚类会引入较多主观阈值，适合后续版本。

### 决策 4：行为聚类与参数覆盖率绑定解释类型

**选择**：每个完全重复簇必须被归类为：
- `expected_same_behavior`
- `inactive_parameter_cluster`
- `shadowed_behavior_cluster`
- `suspicious_same_behavior`

**备选方案**：
- 只输出“重复簇”，不做原因解释

**理由**：重复本身不一定是 bug。系统必须区分“市场没有给参数触发机会”和“参数逻辑被覆盖”这两类完全不同的问题，否则 shortlist 会误删正常结果或放过真实异常。

### 决策 5：局部最优选择以 `strategy + symbol + interval` 为唯一分组单位

**选择**：每个组内先过滤掉审计失败、可疑簇成员和明显不适合实盘的组合，再在剩余组合中选择一个代表参数。

**备选方案**：
- 全局直接按综合分排序
- 只按 `symbol + interval` 分组，忽略策略名称

**理由**：这与未来实盘使用方式一致，也能避免强势市场的海量参数占满榜单。策略维度必须保留，否则不同策略会被错误混合。

### 决策 6：shortlist 只消费局部 winner，不直接面对原始组合

**选择**：shortlist 的输入单位是 `local_best` winner，而不是所有优化样本。shortlist 只负责决定哪些局部冠军值得进入实盘候选池。

**备选方案**：
- 直接从全量组合中选 top N

**理由**：只有这样才能避免重复行为和同一市场下多个近似参数霸榜，也更符合“每个市场只保留最佳参数”的目标。

### 决策 7：未分类退出不是业务类型，而是异常信号

**选择**：移除“其他原因退出”作为正常业务分类，兜底只保留 `unclassified_exit / 未分类退出`，并在 audit 中单独统计与告警。

**备选方案**：
- 保留“其他原因退出”作为正常分类

**理由**：对于当前框架，绝大多数退出路径都可以归因到具体机制。继续保留“其他原因”会掩盖真实 bug，让系统失去异常自检能力。

## Risks / Trade-offs

- **参数覆盖率规则过于宽松，导致 bug 漏报** → 先覆盖最关键的 6 个参数，明确每类参数的触发证据与效果证据
- **参数覆盖率规则过于严格，误把未触发当异常** → 引入 `no_opportunity` 和 `inactive` 区分，并在审计中保留证据字段
- **行为指纹字段过少，导致误把不同策略视为相同** → Exact fingerprint 基于逐笔交易和关键风控字段，不只看 summary 指标
- **HTML 视图与机器结果不一致** → 所有 HTML 只消费 JSON 产物，不在前端重新推导异常结论
- **Agent 审查替代脚本审计** → workflow 中硬规则审计始终在前，Agent 只做二次语义判断

## Migration Plan

1. 扩展单次回测报告字段，使其能承载退出原因与风控中间状态
2. 在 optimization run 完成后新增参数覆盖率与行为指纹生成步骤
3. 新增行为聚类与局部最优选择器，先仅支持 BTC-1d 基线
4. 基于上述产物新增 shortlist 输出
5. 把 audit + clustering 结果接入自动化脚本和 Agent review workflow
6. 待单市场基线稳定后，再推广到多币种、多周期和多策略

回滚策略：
- 若 V1 出现问题，可保留原始 optimization pipeline 和现有 `rankings` 输出，同时禁用新增审计/shortlist 产物，不影响原有回测执行

## Open Questions

- `local_best` 的实盘过滤阈值（最少交易数、最大回撤、未分类退出比例）应采用固定默认值还是完全配置化
- V1 是否需要在 shortlist 中输出候补项，还是只输出主候选与拒绝原因
- Similar behavior clustering 是否应在 V1 留下接口但不启用，还是完全延后到后续 change
